# D04｜SeeMind 文旅场景智能体方案

**版本：v0.2（部门审阅稿）**  
**日期：2026-10-22**  
**适用：景区管理方、运营公司、数字化建设部门**  
**范围说明：** 本稿为可迁移的通用方案。涉及九华山、嵩山等具体景区的系统现状、可接入数据、既有合作和建设效果，须取得项目资料后才可改写为客户版。本文区分“现有产品描述”“建议建设功能”“演示假设”，不以假设替代事实。

## 01｜项目概述（通用正文）

景区运营中的客流、停车、交通、索道、环境和服务状态持续变化。游客希望得到当前可执行的游览建议，管理人员希望基于同一组实时信息快速判断问题并安排处置。传统分散系统提供单一数据，跨系统的理解与行动仍主要依赖人工。

本方案建议将 SeeMind 的物理世界理解能力与 World State 状态层引入文旅场景，形成“统一状态、自然语言查询、趋势辅助判断、人工确认行动、结果反馈”的业务闭环。四类角色共用一个状态底座，减少各端信息不一致的问题。

**项目目标**

- 运营人员能够查询景区当前状态，追溯答案来源。
- 管理人员能够比较不同调度方案及其约束。
- 一线人员能够接收事件、反馈处置并保留核验记录。
- 游客能够得到结合当前状态的路线与到达建议。

以上为拟建设目标，项目验收指标应由试点阶段的实测基线决定。

## 02｜业务问题与切入场景（通用正文）

| 业务问题 | 典型提问 | 推荐建设能力 |
|---|---|---|
| 状态信息分散 | “现在停车、排队和山顶天气如何？” | 多源状态统一查询 |
| 局部客流突增 | “过去 30 分钟哪个区域压力上升？” | 变化检测与热点研判 |
| 路线随时变化 | “现在出发还能赶上日落吗？” | 有约束的动态行程建议 |
| 设施运行变化 | “索道临时停运后怎么分流？” | 影响范围分析与备选方案 |
| 一线处置缺少闭环 | “现场是否已经完成处理？” | 事件派单、回传、复核 |
| 游客与管理口径不一致 | “景区公告和问答是否同步？” | 统一事实来源与更新时间 |

优先试点能够获取数据、触发明确业务动作、容易验证结果的场景。

## 03｜系统组成与边界（通用正文）

**数据接入层**：按授权接入景区内部业务系统、视频事件、停车运行、天气和公开信息。接入方式可以是 API、事件订阅或经许可的设备数据，具体方式由现网条件决定。

**World State 层**：按位置、时间、实体、事件及数据来源组织当前状态，保留更新时刻和版本变化。对冲突数据标识来源差异，对过期数据作出提示。

**SeeMind 判断层**：提供跨数据源查询、事件理解、趋势研判和备选行动建议。模型的推断必须与观测事实分开展示。

**业务应用层**：四类入口共享状态层；涉及调度、派单、通知发布或外部动作时，默认经授权人员确认。

**最小事实输出字段**：问题、结论、适用时间、空间范围、数据来源、更新时刻、可信程度或条件限制、建议动作。

> 能力边界：是否可自动派单、预测多少分钟后的状态、是否可获取视频或票务数据，均取决于授权、系统联调与验证结果。通用方案不得将其描述为目标景区现有能力。

## 04｜数据资源清单（待景区确认）

| 数据 | 最低需要确认的字段 | 更新要求 | 可支撑的业务 |
|---|---|---|---|
| 客流 | 区域 ID、人数/密度、统计时间、来源 | 按业务场景确定 | 热点监测、拥堵预警 |
| 停车 | 车场 ID、容量、空余数、入口状态、采样时间 | 接近实时 | 入园路径和停车建议 |
| 索道/接驳 | 站点、开闭状态、预计排队、运力、更新时间 | 运行中高频 | 行程可达性、分流 |
| 道路 | 路段、拥堵/通行状态、交通限制 | 接近实时 | 到达与场内路线 |
| 气象 | 观测位置、时间、降雨/风力、预警 | 随官方预警更新 | 设施安全、行程提示 |
| 票务/营业 | 名额、开放时段、停售/关闭状态 | 与业务系统同步 | 可执行推荐 |
| 工单 | 事件类型、位置、责任人、状态、时间戳 | 业务事件触发 | 处置与效果核验 |

## 05｜运营中心：全域态势（通用正文）

**页面结构建议**

1. 主画布显示景区地图、区域层级、重点设施和实时事件，避免密集装饰图形遮挡底图。
2. 上方只保留关键状态：当前客流、趋势、重点区域压力、设施运行与异常事件。
3. 侧边显示当前影响运营的事项，允许按区域、时间和事件类型筛选。
4. 点击一个区域，展示证据、趋势、相关设施和可采取的调度动作。

**典型操作**

- “当前哪三个区域客流增长最快？”
- “如果东侧停车场满位，会影响哪些入口？”
- “索道停运将影响哪些已规划游线？”

系统回答必须标注所用数据源、观察时刻与模型推断内容。不能把尚未建立的数据指标放入演示真值栏。

## 06｜管理智能体：判断与调度（通用正文）

建议把管理动作拆成六步：

1. **提问**：自然语言输入运营问题。
2. **取证**：从 World State 读取涉及的实体、位置、时间和状态。
3. **比较**：形成至少一个可行方案及其条件、限制和代价。
4. **确认**：管理人员选择或修改方案。
5. **执行**：向有权限的工单或通知系统发送动作。
6. **核验**：记录完成情况及现实结果，用于复盘。

示例：某入口压力升高。系统提出“临时开放备用入口”与“增加摆渡班次”两种建议，说明各自需要的条件。业务负责人确认后执行，最终比较入口排队变化。**这是设计情景，实际调度能力需依据现场系统验证。**

## 07｜一线治理 App：处置闭环（通用正文）

**事件卡片的最小内容**

| 字段 | 要求 |
|---|---|
| 事件 | 类型、简述、发生时间 |
| 位置 | 景区区域与具体点位 |
| 证据 | 来源、可查看的现场证据、采集时间 |
| 责任 | 处理岗位、优先级、操作权限 |
| 状态 | 待派单、处理中、待复核、已关闭 |
| 结果 | 处置说明、照片/记录、复核人、完成时刻 |

在试点中优先复用景区原有工单系统。如果现有平台无法打通，再讨论独立一线应用，避免增加重复操作。

## 08｜游客助手：动态游览（通用正文）

游客关注的核心不是抽象数据，而是“我现在应该怎么做”。输入可以是目的、同行人、体力偏好、时间窗口和当前位置，系统结合实时状态给出可执行建议，并在关键约束改变时提示重新规划。

**三类标准问答**

- **出发判断**：“现在去主峰是否合适？”展示天气、上山耗时、排队和开放状态。
- **路线取舍**：“带孩子、少爬坡，还能看到云海吗？”展示不同路线的行走量、用时和可到达性。
- **变化应对**：“索道排队突然变长，原计划还来得及吗？”标明新旧方案差别及调整原因。

**演示情景（模拟数据，禁止当作项目业绩）**

游客希望在 19:02 前到达日落点。起初索道排队约 30 分钟，系统建议先就餐并游览听松台；当凌云栈道人流过多且索道排队减少时，重新比较路线，建议放弃拥挤栈道，返回索道站乘缆车前往云海台，再步行至日落点。界面同步给出原因、时间预算和备选路线。

交互原则：输入框方便点按，答案像对话流逐步展开，地图只展示与决策有关的真实区域和路线，证据卡片在需要时出现。

## 09｜实施计划与验收（待景区确认）

| 阶段 | 工作重点 | 退出条件 |
|---|---|---|
| A 现状核查 | 数据权属、设备清单、流程访谈、系统边界 | 数据清单与业务范围签字确认 |
| B 最小试点 | 选取一处停车场、一条主要游线、一个事件类型 | 数据可用、问答可追溯、人工能纠错 |
| C 业务联调 | 管理调度与处置平台打通 | 事件从发现到复核全流程留痕 |
| D 扩展运营 | 拓展覆盖范围和用户入口 | 运营数据稳定、指标达到双方约定目标 |

可选验收指标：信息新鲜度、可回答问题覆盖率、证据完整率、人工复核正确率、工单闭环时长、游客实际采纳率。**暂不承诺具体数值**，先设测量方法和基线。

## 10｜商务与项目边界（待景区确认）

商务讨论可拆分为平台能力服务、现场系统集成、数据治理、实施培训与持续运维。按场景包订阅是否适用，还需判断采购方性质、部署条件与现有 IT 合同边界。

正式报价前，须确认以下五项：

1. 采购主体与建设目标
2. 接入数据范围及授权/脱敏责任
3. 私有化或云端部署要求
4. 工单、票务及运营系统的集成范围
5. 服务等级、培训、验收和运维责任

未经确认，不填写金额、周期、项目收益或节约成本。
